## 0. Update 2026-11-25 — the host is Cloudflare Pages now

Date-stamped because the rest of this document is a 2026-11-21 record: where it says
Netlify publishes `dist/`, that was true when written and is not true now.

- **Production is Cloudflare Pages**, project `waxwing`, custom domain
  `waxwinglandscaping.com` (preview host `waxwing-dc3.pages.dev`). Apex serves 200,
  `www` 301s to it, every canonical uses the apex.
- **Deploys are manual direct uploads** from this machine:
  `python3 build.py` → `python3 check_links.py --quiet` →
  `python3 docs/deploy-pages.py --apply` → `--check`. Nothing builds on push, so a
  green CI run does not mean production moved; and the build that ships is the one
  built here, not one a host rebuilt from the commit.
- **`netlify.toml` is no longer a publish config.** The old host
  `groundworkllc.netlify.app` is a 301-only site (`docs/netlify-retire/_redirects`).
  Do not read its `[build]` block as the deploy path.
- **Cache headers come from `dist/_headers`**, generated by `build.py`, not from
  `netlify.toml`. Both names are emitted because both hosts read `_headers`.
- **Credential trap:** the Cloudflare key in `~/.secrets/cloudflare.key` is
  account-scoped — it passes `/accounts` and `/zones` and is refused by
  `/accounts/{id}/pages/projects` — so `deploy-pages.py` proves Pages access first
  and falls back to the wrangler OAuth session. `docs/handshake.py --receipt` shows
  the last permission check.

## 4a. The domain switch, when the domain exists

Prepared 2026-11-21. **Steps 2–4 run 2026-11-22**, after the domain was bought: source
flipped (58 files), `build.py` exit 0, `check_links.py --quiet` clean, `dist/` has 0
files naming the old host and 43 naming the new one, 37/37 sitemap `<loc>`s re-rooted,
`robots.txt` correct, and the `[[redirects]]` block below is in `netlify.toml`. **Step 1
(add the domain to the Netlify site) was superseded**: the domain was attached to Cloudflare
Pages instead (§0), so nothing above depends on Netlify serving the site — it only 301s the
old host. `build.py` now derives every absolute URL it emits from one
constant, `SITE`, and `build_sitemap()` re-roots each `<loc>` on it — so `sitemap.xml` can
keep whatever host it has and cannot drift from the constant.

1. **Superseded — skipped.** The plan was to add `waxwinglandscaping.com` to the Netlify
   site (`groundworkllc`) under **Domain management**, via Netlify DNS or the registrar's
   records. Instead the domain was attached to Cloudflare Pages (§0), which creates the
   proxied CNAME itself and issues the certificate.
2. Flip the host in the source. This one literal is the whole switch:

   ```bash
   grep -rl 'groundworkllc\.netlify\.app' . --exclude-dir=.git --exclude-dir=dist \
     --exclude-dir=claudplan4gg --exclude-dir=dev-archive --exclude-dir=__pycache__ \
     | xargs sed -i 's/groundworkllc\.netlify\.app/waxwinglandscaping.com/g'
   ```

   It covers `SITE`, every hand-written canonical and JSON-LD `url`, `robots.txt`,
   `url.txt`, and the `_next` redirect in `site.js`. Proven complete on a copy of the tree:
   after that sed and a build, `grep -rl groundworkllc dist` returns 0 files and 41 carry
   the new host. The old host's live URL is worth keeping, so the flip does not delete it.
3. `python3 build.py && python3 check_links.py --quiet`.
4. 301 the old host, for a year, and keep the `netlify.app` name on the site so it can fire.
   **Applied 2026-11-22** in `netlify.toml`, above the `[[headers]]` blocks:

   ```toml
   [[redirects]]
     from = "https://groundworkllc.netlify.app/*"
     to = "https://waxwinglandscaping.com/:splat"
     status = 301
     force = true
   ```

   The `from` is scoped to the old host deliberately. A bare `"/*"` would match the new
   domain too and redirect it to itself; the rule must name the netlify.app host to be
   safe. Verify after the first deploy: `curl -I https://groundworkllc.netlify.app/work.html`
   must return `301` with a `location` on the new host, and
   `curl -I https://waxwinglandscaping.com/work.html` must return `200`, not `301`.

5. New Search Console property → submit `sitemap.xml` → request indexing on the five money
   pages. The old property is empty (0 impressions, nothing ever submitted), so there is no
   history to lose.
6. Then the GBP — after the LLC and insurance (`BRAND_AND_LAUNCH.md` §5).

## 5. Traps

- **`dist/`, `claudplan4gg/` and `dev-archive/` are full copies of the site.** A blanket
  `sed` across the repo rewrites build output and historical records. This is the single
  easiest way to make a mess here.
- **`dist/` is what ships**, via `python3 build.py` then
  `python3 docs/deploy-pages.py --apply`; a source edit that is never built and uploaded
  never goes live. `netlify.toml` publishes nothing any more — it is the old host's 301
  record. The build also minifies HTML (so `dist/` never diffs cleanly against source) and
  regenerates the five PDFs in `docs/marketing/`.
- **`site.js` maps `?service=` to an `<option>` in `contact.html`.** A new service page
  without a matching option fails silently — the form just arrives unselected.
- **`theme-lab.html` is a lab page**, absent from `sitemap.xml`. Delete it rather than
  let it drift.
- **`blog-post-7`'s title is 83 characters and `landscape-design-longmont`'s description
  is 162** — both predate this session and are over the usual limits. Not caused by any
  change here; trim them when those pages are next opened.
- The `#testimonials` id survives in `work.html` only. It is a live section heading,
  not a leftover.
